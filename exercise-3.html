🛒 SmartShop 2 — Permissions, Decorators & Custom Users

Extend the earlier SmartShop application that already introduced Django Messages, Sessions and Cookies. This exercise adds authentication, a custom user model, roles, Django's built-in permissions, protected views, decorators and polished templates.

1. Where This Exercise Starts

Important: The earlier SmartShop exercise already covered the Messages Framework, Sessions and Cookies. This exercise keeps those ideas and builds the next layer on top: who the user is, what the user is allowed to do, and how Django protects views.
Browser ↓ Django URL ↓ Authentication ↓ Is the request user logged in? ↓ Permissions / role checks ↓ Decorator-protected view ↓ Messages + Session + Cookies ↓ Django Template

The final SmartShop application will have two broad experiences:

Customer area

Login, browse products, maintain the session cart, save preferences in cookies, and see feedback messages.

Shop manager area

Access a protected dashboard and product-management actions only when the authenticated user has the required permission.

Authentication ≠ Authorization.
Authentication identifies a user. Authorization decides what that authenticated user can access or do.

3. A Critical Django Decision: Custom User Model

Django provides a built-in user model. That is convenient, but real applications often need additional account information such as a role, employee code, phone number, department or other business-specific fields.

For this exercise, we will create a custom user model using Django's AbstractUser.

Why AbstractUser? It keeps Django's normal username/password, groups, permissions and authentication behavior, while allowing us to add our own fields. It is usually much easier to extend than implementing authentication completely from scratch.
Very important: Django projects should normally define AUTH_USER_MODEL before the first migration that creates user-related tables. Changing the user model after a project has already accumulated migrations and relationships can require significant migration work. Since the earlier SmartShop project already exists, the cleanest learning setup is to create a fresh database/project copy for this extension, or reset the development database before introducing the custom user model.

5. Create the Custom User Model

Open accounts/models.py:

from django.contrib.auth.models import AbstractUser
from django.db import models


class User(AbstractUser):
    ROLE_CHOICES = [
        ("customer", "Customer"),
        ("manager", "Shop Manager"),
    ]

    role = models.CharField(
        max_length=20,
        choices=ROLE_CHOICES,
        default="customer"
    )

    department = models.CharField(
        max_length=100,
        blank=True
    )

    def __str__(self):
        return self.username

Understand every piece

AbstractUserDjango's reusable user implementation containing standard authentication fields and behavior.
class User(AbstractUser)Creates our own user model while inheriting the standard Django user functionality.
ROLE_CHOICESA list of allowed role values and their human-readable labels.
roleA database field storing the user's broad application role.
choices=ROLE_CHOICESRestricts the normal form/admin selection to the defined choices.
blank=TrueAllows the field to be left empty in Django form validation.
__str__Controls how the user is represented as text in the admin and other displays.

11. Understand Django's Built-in Permission System

Django automatically creates model permissions such as:

  • add — can create objects
  • change — can modify objects
  • delete — can remove objects
  • view — can view objects

For a model named Product in an app named store, a permission may be represented as:

store.add_product store.change_product store.delete_product store.view_product

The format is app_label.codename.

Important distinction: A role such as manager is our application's business concept. A Django permission is an explicit authorization capability. Groups can be used to bundle permissions together.

12. Create a Product Model

To make permissions meaningful, replace the earlier simple product list with a database model. In store/models.py:

from django.db import models


class Product(models.Model):
    name = models.CharField(max_length=120)
    category = models.CharField(max_length=80)
    price = models.DecimalField(max_digits=10, decimal_places=2)
    stock = models.PositiveIntegerField(default=0)

    def __str__(self):
        return self.name

Now create and apply the migration:

python manage.py makemigrations
python manage.py migrate

Django will create the four standard permissions for Product automatically.

13. Create a Manager Group

Groups provide a convenient way to assign a collection of permissions to multiple users.

In the Django admin:

  1. Open Groups.
  2. Create a group called Shop Managers.
  3. Give it Product permissions such as view, add and change.
  4. Save the group.
  5. Open a user account.
  6. Add that user to Shop Managers.
Why groups? Imagine 20 managers. Instead of manually assigning the same permissions to each person, define the permission set once in a group and assign users to the group.

18. The First Decorator: login_required

Suppose the manager dashboard should not be accessible to anonymous visitors.

from django.contrib.auth.decorators import login_required
from django.shortcuts import render


@login_required
def dashboard(request):
    return render(request, "store/dashboard.html")

What is a decorator?

A decorator is Python syntax that wraps a function and adds behavior without rewriting the function's core body.

Request ↓ @login_required ↓ Is user authenticated? ├── No → redirect to login └── Yes → run dashboard()

The @login_required line is therefore a protection layer around the view.

19. Add Permission Protection

Login alone is not enough. A logged-in customer should not automatically be allowed to manage products.

from django.contrib.auth.decorators import login_required, permission_required


@login_required
@permission_required("store.view_product", raise_exception=True)
def product_dashboard(request):
    return render(request, "store/product_dashboard.html")

Read the decorators from top to bottom

@login_required ↓ User must be logged in ↓ @permission_required(...) ↓ User must have store.view_product ↓ product_dashboard()

raise_exception=True tells Django to raise a permission-related exception rather than redirecting to the login page when the user is authenticated but lacks the permission.

20. Permission Checks Inside a View

A decorator is excellent when an entire view requires a permission. Sometimes the view needs conditional behavior.

from django.contrib import messages
from django.shortcuts import redirect, render


def products(request):
    can_add = request.user.has_perm("store.add_product")

    return render(
        request,
        "store/products.html",
        {"can_add": can_add}
    )

Now the template can conditionally display an Add Product button.

{% if can_add %}
  <a href="{% url 'store:add_product' %}" class="btn btn-primary">
    + Add Product
  </a>
{% endif %}
Do not rely only on hiding a button. A user can type a URL manually. The view itself must enforce authorization. Template checks improve the interface; decorators/permission checks protect the actual endpoint.

21. Create Product Views

In store/views.py:

from django.contrib import messages
from django.contrib.auth.decorators import login_required, permission_required
from django.shortcuts import get_object_or_404, redirect, render

from .models import Product


def products(request):
    items = Product.objects.all()
    return render(request, "store/products.html", {"products": items})


@login_required
@permission_required("store.add_product", raise_exception=True)
def add_product(request):
    if request.method == "POST":
        name = request.POST.get("name", "").strip()
        category = request.POST.get("category", "").strip()
        price = request.POST.get("price", "0")
        stock = request.POST.get("stock", "0")

        if not name or not category:
            messages.error(request, "Name and category are required.")
            return render(request, "store/add_product.html")

        Product.objects.create(
            name=name,
            category=category,
            price=price,
            stock=stock
        )

        messages.success(request, "Product added successfully.")
        return redirect("store:products")

    return render(request, "store/add_product.html")

Here the earlier Messages Framework is being reused: successful and invalid operations produce temporary feedback.

22. Protect Product Editing

@login_required
@permission_required("store.change_product", raise_exception=True)
def edit_product(request, product_id):
    product = get_object_or_404(Product, id=product_id)

    if request.method == "POST":
        product.name = request.POST.get("name", "").strip()
        product.category = request.POST.get("category", "").strip()
        product.price = request.POST.get("price", "0")
        product.stock = request.POST.get("stock", "0")
        product.save()

        messages.success(request, "Product updated successfully.")
        return redirect("store:products")

    return render(
        request,
        "store/edit_product.html",
        {"product": product}
    )

get_object_or_404() is a Django shortcut. It retrieves the object or automatically returns a 404 response when it does not exist.

23. Delete Protection

@login_required
@permission_required("store.delete_product", raise_exception=True)
def delete_product(request, product_id):
    product = get_object_or_404(Product, id=product_id)

    if request.method == "POST":
        product.delete()
        messages.success(request, "Product deleted.")
        return redirect("store:products")

    return render(
        request,
        "store/confirm_delete.html",
        {"product": product}
    )
Use POST for destructive operations such as deletion. Avoid designing a delete action that changes data through a simple GET link.

28. A Custom Decorator for the Manager Role

Django's login_required and permission_required solve common authorization problems. Sometimes an application also needs a business-specific rule, such as “only users whose role is manager may enter this page.”

Create store/decorators.py:

from functools import wraps

from django.contrib import messages
from django.shortcuts import redirect


def manager_required(view_func):
    @wraps(view_func)
    def wrapper(request, *args, **kwargs):
        if not request.user.is_authenticated:
            return redirect("login")

        if request.user.role != "manager":
            messages.error(
                request,
                "You need a manager account to access this page."
            )
            return redirect("store:home")

        return view_func(request, *args, **kwargs)

    return wrapper

Understand the helper pieces

wrapsPreserves useful metadata from the original view function when it is wrapped.
view_funcThe original Django view function being protected.
*args, **kwargsAllows the wrapper to accept whatever positional and keyword arguments Django passes to the view.
request.userThe currently authenticated user associated with the request.
request.user.roleOur custom field from the User model.
return view_func(...)If the checks pass, execute the original view.

29. Use the Custom Decorator

Import it into views.py:

from .decorators import manager_required

Then protect a manager-only dashboard:

@manager_required
def manager_dashboard(request):
    products_count = Product.objects.count()

    return render(
        request,
        "store/manager_dashboard.html",
        {"products_count": products_count}
    )

This is a useful example of combining the custom user model with a custom decorator. The permission system and role system are different mechanisms and can coexist.

31. Custom User Model + Messages + Sessions

The new concepts connect naturally to the earlier exercise.

User logs in ↓ Django authentication ↓ Authentication information stored through session mechanism ↓ request.user available in later requests ↓ Permission / role check ↓ View executes ↓ messages.success(...) ↓ Next page displays one-time feedback

The exact session storage details depend on Django's configured session backend, but the default project setup uses database-backed sessions.

32. Add a Session-Based “Last Seen” Feature

Use a session to remember a value across requests.

from django.utils import timezone


def home(request):
    visits = request.session.get("visits", 0)
    visits += 1
    request.session["visits"] = visits

    return render(
        request,
        "store/home.html",
        {"visits": visits}
    )

This continues the previous Sessions concept. The user's login identity and application session data are separate ideas, but both rely on Django's session mechanism.

33. Continue Using Cookies for Preferences

Cookies are still useful for small browser-side preferences such as a display theme.

from django.shortcuts import redirect, render


def preferences(request):
    theme = request.COOKIES.get("theme", "light")

    return render(
        request,
        "store/preferences.html",
        {"theme": theme}
    )


def set_theme(request, theme):
    response = redirect("store:home")
    response.set_cookie("theme", theme, max_age=60 * 60 * 24 * 30)
    return response

Do not store passwords or sensitive authentication information in ordinary cookies created this way. Authentication cookies are managed by Django's authentication/session system.

40. Understand Decorator Order

For:

@login_required
@permission_required("store.add_product", raise_exception=True)
def add_product(request):
    ...

The decorators wrap the function. Keeping authentication before authorization expresses the natural security flow: first establish that a user is authenticated, then evaluate whether that user has the required capability.

41. Custom Decorator with functools.wraps

It is worth understanding why @wraps is not just decorative syntax.

from functools import wraps

def my_decorator(view_func):
    @wraps(view_func)
    def wrapper(request, *args, **kwargs):
        # extra behavior
        return view_func(request, *args, **kwargs)

    return wrapper

Without wraps, metadata such as the wrapped function's name and documentation can be replaced by the wrapper function. wraps preserves that useful metadata.

42. A Cleaner Permission Decorator for One Permission

You can also build a small reusable decorator when a particular business rule appears repeatedly:

from functools import wraps
from django.core.exceptions import PermissionDenied


def require_product_management(view_func):
    @wraps(view_func)
    def wrapper(request, *args, **kwargs):
        if not request.user.is_authenticated:
            raise PermissionDenied

        if not request.user.has_perm("store.change_product"):
            raise PermissionDenied

        return view_func(request, *args, **kwargs)

    return wrapper

This example shows that decorators are simply reusable Python functions. Django's built-in decorators are preferable when they already solve the problem; custom decorators are useful when the application has a repeated rule of its own.

43. Why Not Put All Authorization in Templates?

Consider:

{% if perms.store.delete_product %}
  <a href="...">Delete</a>
{% endif %}

This is good UI behavior because users should not see controls they cannot use. But it is not enough as security.

Template hiding ≠ Server-side authorization Good application: Template hides unauthorized control + View rejects unauthorized request

44. Custom User Model: When to Add Fields

The custom user model should contain information that is genuinely part of the identity/account domain. For example:

  • Role
  • Department
  • Employee code
  • Phone number
  • Account-specific preferences

Do not put every unrelated business record directly into the User model. For more complex profiles, a separate profile model related to the user can be more appropriate.

The important design lesson is to decide the user model early. Authentication models are foundational because many other database tables and authentication components may reference them.
