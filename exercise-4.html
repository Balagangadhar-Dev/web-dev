🔵 1B. JSX: Understand It Before Memorizing Its Rules

JSX is often the first confusing React topic because it looks like HTML but lives inside JavaScript.

function Welcome() {
  const name = "Alex";

  return (
    <div>
      <h1>Hello {name}</h1>
      <p>Welcome to MovieBoard</p>
    </div>
  );
}

Read the code in two directions

JavaScript direction: const name = "Alex" creates data.

UI direction: <h1>Hello {name}</h1> describes what should appear.

The curly braces are the bridge between them. Inside JSX, {name} means: “evaluate this JavaScript expression and place its result here.”

JavaScript value ↓ { name } ↓ JSX ↓ rendered UI

What can go inside { }

<p>{name}</p>
<p>{2 + 3}</p>
<p>{movie.name}</p>
<p>{isLoggedIn ? "Logout" : "Login"}</p>

The important word is expression. JSX can display the result of an expression. It is not a place to write arbitrary JavaScript statements.

🔵 1C. JSX vs HTML — Why Does React Change the Syntax?

HTMLJSXReason
classclassNameJSX uses JavaScript-oriented property naming.
onclickonClickReact event props use camelCase.
Multiple top-level elementsOne enclosing tree/FragmentA component returns one JSX tree.
Plain text onlyCan embed JavaScript expressionsJSX is part of JavaScript source.
Do not think “React changed HTML.” Think “JSX is a JavaScript syntax that looks similar to HTML because UI markup is easier for humans to read that way.”

🧩 1D. What Exactly Is a Component?

A component is not simply “a file” and not simply “some HTML.” A component is a reusable unit that describes part of the UI and can contain the logic/data needed for that part.

function MovieCard() {
  return (
    <article>
      <h2>Inception</h2>
    </article>
  );
}

The function is the component definition. When React encounters:

<MovieCard />

it uses that component to produce the corresponding UI.

Important distinction: MovieCard.jsx is a file; MovieCard is the component; <MovieCard /> is JSX that asks React to render that component.

🧩 1E. Function Component: Read It Like a Normal JavaScript Function

function MovieCard({ movie }) {
  return (
    <article>
      <h2>{movie.name}</h2>
    </article>
  );
}

Start from the outside:

  1. function MovieCard(...) creates a JavaScript function.
  2. { movie } receives one property from the props object.
  3. return gives React the UI description.
  4. {movie.name} reads JavaScript data and inserts it into JSX.
Therefore: a function component is still a JavaScript function. React gives that function a special role: its returned value describes part of the UI.

📦 1F. Props: The Most Useful Mental Model

Think of a component as a function with named inputs.

function add(a, b) {
  return a + b;
}

add(10, 20);

Similarly, a component can receive named inputs:

<MovieCard
  name="Inception"
  year={2010}
/>

Inside:

function MovieCard(props) {
  console.log(props);

  return (
    <h2>{props.name}</h2>
  );
}

Conceptually, React gives the component an object like:

{
  name: "Inception",
  year: 2010
}

That object is the component's props.

Why are props important?

Without props, every MovieCard would need hard-coded information. With props, one component can display hundreds of different movies.

📦 1G. Props Are Not “Global Variables”

Props belong to the relationship between a parent and child component.

App │ │ movie={movie} ↓ MovieCard │ └── reads movie from props

This is different from a global variable. The parent explicitly provides the data to the child.

One-way data flow: Parent → Child. A child does not automatically reach into its parent's state and change it.

🏛️ 1I. Why Does a Class Component Use this?

this is JavaScript class syntax. It refers to the current object/instance.

class MovieCounter extends Component {
  constructor() {
    super();
    this.state = { count: 0 };
  }

  render() {
    return <p>{this.state.count}</p>;
  }
}

Here this.state means the state belonging to this component instance.

Likewise, this.props means the props belonging to this component instance.

Simple reading rule: when you see this.state, read it as “this component's state.” When you see this.props, read it as “this component's props.”

⏱️ 1J. Lifecycle: Understand the Story, Not Just the Method Names

Imagine placing a MovieCard on the screen, changing its favorite status, and then removing it.

Component created ↓ MOUNT ↓ Component is visible ↓ UPDATE ↓ State/props change ↓ Component is rendered again ↓ UNMOUNT ↓ Component is removed

The lifecycle methods are hooks into this story.

Mount: “The component has appeared.”

Update: “Something affecting the component changed.”

Unmount: “The component is going away.”

The reason lifecycle matters is not the names themselves. The reason is timing: some work should happen only after a component exists, some work should respond to updates, and some resources must be cleaned up before removal.

⏱️ 1K. Lifecycle Example with a Timer

A timer is a useful mental example because it creates an external resource that needs cleanup.

class Timer extends Component {
  componentDidMount() {
    this.timerId = setInterval(() => {
      console.log("tick");
    }, 1000);
  }

  componentWillUnmount() {
    clearInterval(this.timerId);
  }

  render() {
    return <p>Timer is running</p>;
  }
}

Why clean it up?

If the component disappears but the interval continues running, the application may keep doing unnecessary work. The cleanup method gives the component a place to release resources it created.

❤️ 1M. Why setState/useState Setter Instead of Direct Assignment?

Consider:

count = count + 1;

This changes a JavaScript variable. It does not communicate the state transition through React's state API.

With React state:

setCount(count + 1);

you are asking React to update the state value and schedule the necessary rendering work.

User action ↓ state setter ↓ React records the new state ↓ component renders with new state ↓ UI reflects the new state

⚖️ 1N. State vs Props — Use Ownership to Understand the Difference

Definitions are useful, but ownership makes the distinction much easier.

If you ask...Think...
“Who gave this value to me?”Props
“Who owns this changing value?”State
“Can this child directly rewrite its parent's value?”No. It receives props; the parent owns its state.
“How can a child request a change?”Call a callback passed by the parent.
Parent owns state │ ├── value ───────→ Child as prop │ └── setter/callback → Child as prop │ ↓ user event │ ↓ callback runs │ ↓ Parent updates state

🔄 1O. The Complete React Data Cycle

Most beginner confusion disappears once this cycle is clear.

1. Component has data ↓ 2. JSX describes UI using that data ↓ 3. Browser displays the UI ↓ 4. User interacts ↓ 5. Event handler runs ↓ 6. State setter is called ↓ 7. React renders with new state ↓ 8. UI reflects the new state

Props fit into this cycle when data is passed from a parent:

Parent state ↓ props ↓ Child UI ↓ callback ↓ Parent state update

🧪 1P. Debugging Exercise: Predict Before You Run

Look at this code before running it:

function Counter() {
  const [count, setCount] = useState(0);

  function increase() {
    setCount(previous => previous + 1);
  }

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={increase}>
        Increase
      </button>
    </div>
  );
}

Think through these questions:

  1. What is the initial value of count?
  2. What happens when the button is clicked?
  3. Where is the new value stored?
  4. Why does the displayed number change?
  5. What is the difference between increase and increase() in the event handler?
Expected reasoning: increase is passed as the event handler. When the click occurs, React calls it. The setter calculates the next state, React renders again, and {count} now displays the updated value.

🧭 1S. What to Look for When Reading Any New React Code

  1. Find the component definition.
  2. Find its props. Ask where each prop comes from.
  3. Find its state. Ask what each state value represents.
  4. Find event handlers. Ask what user action triggers them.
  5. Find state setters. Ask what changes after the event.
  6. Find child components. Follow the props passed to them.
  7. If it is a class, find lifecycle methods.
  8. Trace the data flow from parent to child.
Professional reading habit: Do not read React code only from top to bottom. Trace data ownership and data flow.

🎯 1T. Final “Explain It Yourself” Challenge

Without looking back at the explanations, explain the following chain:

JSX ↓ Component ↓ Props ↓ State ↓ Event ↓ State update ↓ Re-render ↓ Updated UI

Then explain this second chain:

Parent owns state ↓ Parent passes value as props ↓ Child displays the value ↓ Child triggers callback ↓ Parent updates state ↓ New props flow downward
If you can explain these two flows clearly, you have moved beyond memorizing React syntax and started understanding the React programming model.

5. JSX

JSX is syntax that lets us write markup-like UI inside JavaScript. It is transformed by the React toolchain.

function App() {
  const title = "MovieBoard";
  const year = 2026;

  return (
    <div>
      <h1>{title}</h1>
      <p>Current year: {year}</p>
      <p>2 + 3 = {2 + 3}</p>
    </div>
  );
}

export default App;

Curly braces insert JavaScript expressions into JSX.

Important JSX rules

<div className="card">Hello</div>

<button onClick={handleClick}>Click</button>

return (
  <>
    <h1>Title</h1>
    <p>Text</p>
  </>
);

Use className, not class. Use camelCase event names such as onClick. A component must return one JSX tree; a Fragment <>...</> can group elements without adding a DOM element.

13. Class Component State

class MovieCounter extends Component {
  constructor(props) {
    super(props);
    this.state = { count: 0 };
  }

  render() {
    return (
      <div>
        <p>Favorites: {this.state.count}</p>

18. State Is Different from a Normal Variable

A normal variable changing does not tell React to update the UI.

let count = 0;
count = count + 1;

Use state when the value affects rendered UI:

const [count, setCount] = useState(0);
setCount(count + 1);

Never mutate state directly. For arrays, create a new array:

setFavorites([
  ...favorites,
  movie
]);

21. Parent State → Child Props

When the parent owns the changing value, it can pass the value and a callback down.

function App() {
  const [favorite, setFavorite] = useState(false);

  const movie = {
    name: "Inception",
    year: 2010
  };

  return (
    <MovieCard
      movie={movie}
      favorite={favorite}
      setFavorite={setFavorite}
    />
  );
}
function MovieCard({ movie, favorite, setFavorite }) {
  return (
    <article>
      <h2>{movie.name}</h2>
      <p>{favorite ? "Selected" : "Not selected"}</p>
      <button onClick={() => setFavorite(!favorite)}>
        Toggle
      </button>
    </article>
  );
}
This demonstrates one-way data flow: the parent owns state, data flows down as props, and the child can call a callback supplied by the parent.

22. Props Should Not Be Mutated

If a child receives movie, it should not replace the prop directly.

function MovieCard({ movie }) {
  // Treat movie as read-only input.
}

If the movie must change, the component that owns the state should update it and pass the new value down.

State Owner ↓ Parent ↓ props Child

23. Controlled Search Input

function MovieList({ movies }) {
  const [search, setSearch] = useState("");

  const filteredMovies = movies.filter((movie) =>
    movie.name.toLowerCase().includes(
      search.toLowerCase()
    )
  );

  return (
    <>
      <input
        value={search}
        onChange={(event) =>
          setSearch(event.target.value)
        }
        placeholder="Search movies..."
      />

      {filteredMovies.map((movie) => (
        <MovieCard key={movie.id} movie={movie} />
      ))}
    </>
  );
}

value is controlled by state. onChange updates that state. filter() creates the visible list.

24. Function Component Lifecycle with useEffect

Function components do not have componentDidMount() or componentWillUnmount(). Side effects are handled with Hooks such as useEffect.

import { useEffect } from "react";

useEffect(() => {
  console.log("Effect ran after rendering");

  return () => {
    console.log("Cleanup before effect is removed/replaced");
  };
}, []);

The empty dependency array is commonly used when an effect is intended to run after the initial mount and clean up when the component unmounts. useEffect is not a literal one-to-one replacement for every lifecycle method; it is a mechanism for synchronizing with side effects.

31. Final Understanding Check

☐ JSX can be read as a JavaScript-based description of UI.

☐ A component is a reusable unit of UI.

☐ A function component returns JSX.

☐ A class component extends React's Component and uses render().

☐ Class components can use this.props, this.state and setState().

☐ Lifecycle methods describe important stages of a class component.

☐ Function components use Hooks such as useState and useEffect.

☐ Props come from a parent and should be treated as read-only.

☐ State is changing data managed by a component.

☐ State changes cause React to update the rendered UI.

☐ A parent can pass both values and callback functions as props.

☐ State can be lifted to a common parent when multiple components need the same changing value.

32. The Mental Model to Keep

Parent │ │ props ↓ Child │ │ user event ↓ State update │ ↓ React renders again │ ↓ Updated UI
JSX describes the UI. Components organize the UI. Props carry information into components. State stores changing information owned by components. Lifecycle explains what happens as components mount, update and unmount.
