Topic 1.1

Django Architecture & MVC vs MVT Design Pattern

Real-World Analogy: The Restaurant

Imagine visiting a restaurant. You (the Browser) look at the menu and place an order at the front desk (URL Router `urls.py`). The front desk routes your ticket to the Chef (`views.py`). The chef grabs raw ingredients from the Pantry/Fridge (`models.py` / Database), cooks the meal, and hands it to the Food Stylist (`templates/*.html`) who plates it beautifully before serving it back to your table!

Why does Django call it MVT instead of MVC?

Many frameworks use MVC (Model-View-Controller). Django follows the exact same separation of concerns, except Django itself handles the Controller part automatically (routing requests via `urls.py`), leaving you to write the Model, View, and Template.

Component Traditional MVC Django MVT Equivalent File in Django
Data & Database Layer Model Model (Defines database tables) models.py
Business Logic (The Brain) Controller View (Python function/class deciding what data to show) views.py
User Interface (Presentation) View Template (HTML file deciding how data looks) templates/*.html
Traffic Cop / Router Router + Controller Django Framework + URL Dispatcher urls.py

Topic 1.2

Virtual Environments (`venv`) and Project Setup

Beginner Analogy: Separate Tupperware Containers

Suppose Project A needs Django 3.2 (an older recipe) and Project B needs Django 5.1 (the newest recipe). If you install packages globally on your computer, Project B will overwrite Project A and break it! A Virtual Environment (`venv`) creates an isolated bubble (folder) for your project so its Python libraries never clash with other projects.

Terminal — Complete Setup Workflow 
# 1. Create a virtual environment named 'env'
python -m venv env

# 2. Activate the virtual environment
# On Windows:
env\Scripts\activate
# On Mac / Linux:
source env/bin/activate

# 3. Install Django inside the activated environment
pip install django

# 4. Create a new Django project named 'myproject' (notice the dot '.' at the end!)
django-admin startproject myproject .

# 5. Create a modular app inside our project named 'blog'
python manage.py startapp blog

# 6. Start the local development web server
python manage.py runserver
Command-by-Command Breakdown for Beginners
python -m venv env: Tells Python to run its built-in venv module and create an isolated folder called env.
env\Scripts\activate: Turns the bubble ON. You'll see (env) appear at the start of your terminal prompt.
pip install django: Uses Python's package manager (pip) to download Django from the internet into your virtual environment.
django-admin startproject myproject .: Generates the master settings folder. Adding . avoids creating a redundant nested folder.
python manage.py startapp blog: Creates a self-contained feature module ("app") called blog with its own models and views.
python manage.py runserver: Boots up a local server at http://127.0.0.1:8000/ so you can preview your site live!

Topics 1.4 & 1.5

URL Routing, Views, and Rendering Templates with Context Data

Let's trace how to create a real webpage from scratch by wiring together three files: 1) `views.py` (prepare data), 2) `urls.py` (assign a web address), and 3) `home.html` (display the data).

Step 1: blog/views.py 
from django.shortcuts import render
from django.http import HttpResponse

# Simple View returning raw text
def about_view(request):
    return HttpResponse("Welcome to our Bookstore!")

# Template View passing dynamic 'context' dictionary to HTML
def home_view(request):
    context = {
        'student_name': 'Aarav Sharma',
        'course': 'Django Full-Stack Mastery',
        'topics': ['MVT Pattern', 'ORM Queries', 'Authentication', 'REST APIs']
    }
    return render(request, 'blog/home.html', context)
Line-by-Line Breakdown:

def home_view(request): — Every Django view function receives request as its first parameter. It holds info about who is visiting (GET/POST data, logged-in user, browser info).

context = { ... } — A standard Python dictionary. The keys (like 'student_name') become variable names you can use directly inside your HTML file!

return render(request, 'blog/home.html', context) — Combines the HTML template with the context dictionary and returns a finished HTML page to the user's browser.

Step 2: Connecting myproject/urls.py & blog/urls.py 
# --- FILE 1: myproject/urls.py (Master Project Router) ---
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('blog.urls')),  # Forward root URLs to blog/urls.py
]

# --- FILE 2: blog/urls.py (App-Specific Router) ---
from django.urls import path
from . import views

urlpatterns = [
    path('', views.home_view, name='home'),         # Matches http://127.0.0.1:8000/
    path('about/', views.about_view, name='about'), # Matches http://127.0.0.1:8000/about/
]
Line-by-Line Breakdown:

include('blog.urls') — Keeps your project modular! Instead of stuffing 100 URLs into one giant file, the master router delegates URLs to each app's own urls.py.

name='home' — Gives this route a nickname so inside HTML templates you can write {% url 'home' %} instead of hardcoding URLs.

Step 3: blog/templates/blog/home.html (Django Template Language - DTL) 
<!DOCTYPE html>
<html>
<body>
    <!-- Double curly braces {{ }} print variables from context -->
    <h1>Hello, {{ student_name }}!</h1>
    <p>Welcome to {{ course }}</p>

    <!-- Curly brace + percent {% %} runs logic like loops and if-statements -->
    <h3>Syllabus Modules:</h3>
    <ul>
        {% for item in topics %}
            <li>{{ item }}</li>
        {% endfor %}
    </ul>
</body>
</html>
Golden Rule of Django Templates:

{{ variable }} — Double Curly Braces are for displaying values (e.g. printing strings or numbers).

{% tag %} — Curly Brace + Percent is for logic & control flow (e.g., for loops, if conditions, csrf_token, url links).

Topic 2.1

Creating Models and the 2-Step Migration Dance

Beginner Analogy: Architect Blueprint vs Construction Crew

Databases only speak SQL (`CREATE TABLE...`), which is tedious and error-prone to write by hand. In Django, you write a simple Python class called a Model. Then you run two commands:
1. python manage.py makemigrations — The Architect inspects your `models.py` and draws up a blueprint file inside the `migrations/` folder.
2. python manage.py migrate — The Construction Crew reads that blueprint and actually builds the real tables inside `db.sqlite3`!

blog/models.py — Defining a Book Table in Python 
from django.db import models

class Book(models.Model):
    title = models.CharField(max_length=200)
    author = models.CharField(max_length=100)
    price = models.DecimalField(max_digits=6, decimal_places=2)
    is_published = models.BooleanField(default=True)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return f"{self.title} by {self.author}"
Line-by-Line Breakdown:

class Book(models.Model): — Inherits from models.Model, telling Django "Create a database table named blog_book and automatically give it an id primary key column."

models.CharField(max_length=200) — A short text column (VARCHAR(200) in SQL).

auto_now_add=True — Automatically stamps the exact date and time the moment a new Book row is created.

def __str__(self): — Controls how a Book object looks when printed in the Admin panel or shell (instead of showing an unhelpful <Book object (1)>).

Admin Panel Customization & Working with Django Forms (`ModelForm`)

One of Django's "batteries-included" superpowers is its built-in Admin dashboard at `/admin/`. Run python manage.py createsuperuser to create your admin login, then customize how your models appear!

blog/admin.py — Custom Admin Dashboard 
from django.contrib import admin
from .models import Book

@admin.register(Book)
class BookAdmin(admin.ModelAdmin):
    # Columns shown in table list
    list_display = ('id', 'title', 'author', 'price', 'is_published')
    # Adds a search bar searching title & author
    search_fields = ('title', 'author')
    # Adds a right-side filter sidebar
    list_filter = ('is_published', 'created_at')
Why customize `ModelAdmin`? Without `list_display`, Django only shows a single column. Adding `search_fields` and `list_filter` gives you an instant search bar and filter sidebar in 3 lines of code!
blog/forms.py & views.py — ModelForm 
# --- blog/forms.py ---
from django import forms
from .models import Book

class BookForm(forms.ModelForm):
    class Meta:
        model = Book
        fields = ['title', 'author', 'price']

# --- blog/views.py ---
def create_book(request):
    form = BookForm(request.POST or None)
    if request.method == 'POST' and form.is_valid():
        form.save()  # Automatically saves to DB!
        return redirect('home')
    return render(request, 'blog/book_form.html', {'form': form})
`forms.Form` vs `forms.ModelForm`: Use regular `forms.Form` for forms not tied to a DB table (like a Contact Us email form). Use `ModelForm` when creating/updating a database record—it auto-generates inputs and saves with `form.save()`!

Topics 3.1 & 3.2

Built-in Authentication (`login`, `logout`, `authenticate`) & Flash Messages

Never store plain-text passwords! Django's `django.contrib.auth` hashes passwords securely with PBKDF2 and provides three core helper functions: `authenticate()` (checks credentials), `login()` (creates session), and `logout()` (clears session).

accounts/views.py — Complete Registration, Login & Logout with Messages 
from django.shortcuts import render, redirect
from django.contrib.auth import authenticate, login, logout
from django.contrib.auth.forms import UserCreationForm
from django.contrib import messages

# 1. User Registration View
def register_user(request):
    form = UserCreationForm(request.POST or None)
    if request.method == 'POST' and form.is_valid():
        form.save()  # Hashes password & saves new User
        messages.success(request, "Account created successfully! Please log in.")
        return redirect('login')
    return render(request, 'accounts/register.html', {'form': form})

# 2. User Login View
def login_user(request):
    if request.method == 'POST':
        uname = request.POST.get('username')
        pwd = request.POST.get('password')
        # Step A: Verify username & password against database
        user = authenticate(request, username=uname, password=pwd)
        if user is not None:
            # Step B: Attach session cookie so browser stays logged in
            login(request, user)
            messages.success(request, f"Welcome back, {user.username}!")
            return redirect('home')
        else:
            messages.error(request, "Invalid username or password.")
    return render(request, 'accounts/login.html')

# 3. User Logout View
def logout_user(request):
    logout(request)  # Destroys session in DB and clears cookie
    messages.info(request, "You have been logged out.")
    return redirect('login')
Beginner Pitfall — `authenticate()` vs `login()`:

authenticate() only checks if the ID card is genuine and returns the User object (or None). It does NOT log the user in!

login(request, user) actually issues the session wristband so subsequent page loads remember who the user is.

messages.success(request, "...") queues a one-time "flash notification" that disappears after the next page reload.

Topic 3.3

Sessions vs Cookies: How Django Remembers You

Real-World Analogy: Theme Park Wristband (Cookie) vs Secure Locker (Session)

By default, HTTP is stateless (like a goldfish—every time you click a new link, the server forgets who you are!). To fix this:
• Cookie (Stored in Browser): A plastic wristband with a random barcode ID (`sessionid=xyz987`). It holds NO sensitive data.
• Session (Stored in Django's Database): A locked safe behind the counter labeled `xyz987` that stores your actual `user_id`, shopping cart, and permissions!

Topics 4.1 & 4.2

Introduction to REST APIs & DRF Serializers

Why REST APIs & What is a Serializer? (The Universal Translator Analogy)

Standard Django returns HTML pages, which is great for browsers, but what if you also have an Android App, iPhone App, and React Frontend? Mobile apps don't want HTML—they want raw data in JSON format!
A Serializer is a bridge that converts complex Python `Book` model objects into universal JSON text (and validates incoming JSON back into Python objects).

blog/serializers.py & blog/views.py — Complete CRUD API with DRF 
# 1. Install DRF: pip install djangorestframework (and add 'rest_framework' to INSTALLED_APPS)

# --- FILE 1: blog/serializers.py ---
from rest_framework import serializers
from .models import Book

class BookSerializer(serializers.ModelSerializer):
    class Meta:
        model = Book
        fields = '__all__'  # Converts id, title, author, price to JSON!

# --- FILE 2: blog/views.py ---
from rest_framework.decorators import api_view, permission_classes
from rest_framework.permissions import IsAuthenticatedOrReadOnly
from rest_framework.response import Response
from rest_framework import status
from .models import Book
from .serializers import BookSerializer

@api_view(['GET', 'POST'])
@permission_classes([IsAuthenticatedOrReadOnly])
def book_list_api(request):
    if request.method == 'GET':
        books = Book.objects.all()
        serializer = BookSerializer(books, many=True)
        return Response(serializer.data, status=status.HTTP_200_OK)

    elif request.method == 'POST':
        serializer = BookSerializer(data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data, status=status.HTTP_201_CREATED)
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)
Line-by-Line Breakdown:

BookSerializer(books, many=True) — Tells DRF we are serializing a list of multiple books, not just a single book instance.

@permission_classes([IsAuthenticatedOrReadOnly]) — Topic 4.4 in action! Anyone can send a GET request to read books, but only authenticated users with a valid Token/Session can POST, PUT, or DELETE.

            Topic 5.2
            
Django Signals, Middleware Security Gates & Pagination

          


          

            

              
Django Signals

              
Analogy: Smoke Detector. Listens for database events (like `post_save` when a `User` registers) and automatically triggers an action (like creating a blank `Profile` row for that user).

            

            

              
Middleware

              
Analogy: Airport Security Checkpoints. Every HTTP request passes through a chain of gates (Security, Session, CSRF, Auth) before reaching your View, and passes back through on the way out.

            

            

              
Pagination

              
Analogy: Book Chapters. Instead of loading 10,000 products on one slow page, `Paginator(books, 10)` slices results into fast pages of 10 items (`?page=2`).

            

          


          
          

            

              Signals (`post_save`) & Pagination (`Paginator`) Examples
              
            

            
# --- 1. DJANGO SIGNAL: Auto-create Profile when User is saved ---
from django.db.models.signals import post_save
from django.dispatch import receiver
from django.contrib.auth.models import User
from .models import Profile

@receiver(post_save, sender=User)
def create_user_profile(sender, instance, created, **kwargs):
    if created:
        Profile.objects.create(user=instance)

# --- 2. PAGINATION: Split 100 Books into 10 per page ---
from django.core.paginator import Paginator
from django.shortcuts import render
from .models import Book

def book_catalog(request):
    all_books = Book.objects.all()
    paginator = Paginator(all_books, 10)  # Show 10 books per page
    page_number = request.GET.get('page') # Read ?page=2 from URL
    page_obj = paginator.get_page(page_number)
    return render(request, 'catalog.html', {'page_obj': page_obj})
