Django Deployment Masterclass

One Django application. Two real deployments. Build a small Django project locally, prepare it for production, deploy it to PythonAnywhere, and deploy the same project to Heroku.

1. What You Will Learn

This is a single progressive deployment practical. The application is intentionally small so the focus stays on understanding deployment rather than business logic.

Local Django→Git→Production settings→PythonAnywhere+Heroku

Important idea

Deployment is not simply “uploading a folder”. A host needs to know the Python runtime, dependencies, Django settings, entry point, static-file strategy, environment variables, database, and how to start/reload the web process.

Local vs production

LocalProduction
python manage.py runserverProduction web server/platform process
Usually DEBUG=TrueNormally DEBUG=False
localhostPublic domain
Local virtual environmentHosted environment / virtualenv
Django can serve static files during developmentStatic files need a production strategy
Local configurationEnvironment variables/config vars

Core vocabulary

  • WSGI: interface connecting a Python web server to a traditional Django application.
  • Gunicorn: production WSGI server commonly used to run Django.
  • requirements.txt: list of Python dependencies to install.
  • collectstatic: collects static assets into one deployment directory.
  • environment variable: configuration supplied outside the source code.
  • Procfile: Heroku process declaration telling the platform how to start the web process.

2. Build the DeployMe Django Project

2.1 Create the environment

mkdir django-deployme
cd django-deployme
python -m venv venv

Activate it:

macOS/Linux

source venv/bin/activate

Windows PowerShell

venv\Scripts\Activate.ps1

Windows cmd

venv\Scripts\activate
pip install django gunicorn whitenoise

2.2 Create project and app

django-admin startproject deployme .
python manage.py startapp core

2.3 Understand the structure

django-deployme/
├── manage.py
├── deployme/
│   ├── settings.py
│   ├── urls.py
│   ├── wsgi.py
│   └── asgi.py
├── core/
│   ├── views.py
│   └── ...
└── venv/

2.4 Add the app

In deployme/settings.py:

INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "core",
]

2.5 Create a view

In core/views.py:

from django.http import HttpResponse

def home(request):
    return HttpResponse(
        "<h1>DeployMe</h1>"
        "<p>Django deployment is working!</p>"
    )

Understand: the browser sends a request → Django resolves a URL → Django calls home() → the view returns an HTTP response.

2.6 Connect the URL

In deployme/urls.py:

from django.contrib import admin
from django.urls import path
from core.views import home

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", home, name="home"),
]

2.7 Test locally

python manage.py migrate
python manage.py runserver

Open http://127.0.0.1:8000/.

Checkpoint: Do not continue until the application works locally. Hosting cannot repair a broken Django project.

3. Prepare Django for Production

3.1 Record dependencies

pip freeze > requirements.txt

Verify that Django, gunicorn, and whitenoise are present.

3.2 Static files

Add to settings.py:

STATIC_URL = "static/"
STATIC_ROOT = BASE_DIR / "staticfiles"

Run:

python manage.py collectstatic --noinput

Why? Django may find static files in multiple apps during development. collectstatic gathers them into the single directory specified by STATIC_ROOT for deployment.

3.3 WhiteNoise

In MIDDLEWARE, immediately after Django's security middleware:

MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "whitenoise.middleware.WhiteNoiseMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
]

WhiteNoise is a common way to integrate static-file serving into a Django deployment on Heroku. Heroku's official documentation recommends it for this purpose. citeturn1search0

3.4 Environment-aware settings

At the top of settings.py:

import os

Use:

SECRET_KEY = os.environ.get(
    "DJANGO_SECRET_KEY",
    "dev-only-secret-key-change-this"
)

DEBUG = os.environ.get("DJANGO_DEBUG", "True") == "True"

ALLOWED_HOSTS = [
    host.strip()
    for host in os.environ.get("DJANGO_ALLOWED_HOSTS", "").split(",")
    if host.strip()
]

Why? The same Git repository can run in different environments without editing secrets or production hostnames directly into the source.

3.5 Generate a secret

python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
Never commit your production secret key to Git.

3.6 .gitignore

venv/
__pycache__/
*.py[cod]

staticfiles/
.DS_Store

3.7 Git

git init
git add .
git commit -m "Prepare Django app for deployment"

Optional but recommended: push the repository to GitHub. GitHub is useful as your source repository; Heroku Git is a deployment remote, not a substitute for proper source control. Heroku explicitly recommends a source-control system such as GitHub/GitLab/Bitbucket for the canonical repository. citeturn1search5turn1search7

4. Deployment 1 — PythonAnywhere

PythonAnywhere's documented workflow for an existing Django project is: get the code onto PythonAnywhere, create a virtualenv and install requirements, create a Web app using manual configuration, configure its WSGI file, run migrations, configure static files, and reload. citeturn0search0turn0search1

4.1 Account and dashboard

Sign in to PythonAnywhere. The important areas are Files, Consoles, and Web.

For an existing Django project, use the Manual configuration route in the Web tab. The PythonAnywhere documentation specifically distinguishes this from the quickstart intended for new projects. citeturn0search0

4.2 Put the code on PythonAnywhere

If the project is on GitHub:

git clone https://github.com/YOUR_USERNAME/django-deployme.git
cd django-deployme

You can also upload files using the Files interface, but Git makes later updates easier.

4.3 Identify the important paths

Project directory:
 /home/YOUR_PA_USERNAME/django-deployme

Django settings module:
 deployme.settings

Virtual environment:
 /home/YOUR_PA_USERNAME/.virtualenvs/deployme-venv

The project directory is the folder containing manage.py. The settings module is the Python package containing settings.py.

4.4 Create a virtual environment

Use a Python executable/version currently available in your PythonAnywhere account:

mkvirtualenv --python=/usr/bin/python3.12 deployme-venv

If Python 3.12 is not available in your environment, choose an available supported version instead.

cd ~/django-deployme
pip install -r requirements.txt

python --version
pip show django
pip show gunicorn
pip show whitenoise

PythonAnywhere documents virtual environments as the way to use your own package versions rather than relying on the system environment. citeturn0search12

4.5 Database migrations

cd ~/django-deployme
python manage.py migrate

Optional admin account:

python manage.py createsuperuser

4.6 Create the Web app

  1. Open Web.
  2. Choose Add a new web app.
  3. Select your domain.
  4. Choose Manual configuration.
  5. Select the appropriate Python version.

The official existing-Django guide uses this manual configuration flow. citeturn0search0

4.7 Configure the virtualenv

Set the virtual environment path to something like:

/home/YOUR_PA_USERNAME/.virtualenvs/deployme-venv

The Web tab can also accept the short virtualenv name in its appropriate field. citeturn0search0

4.8 Configure source code / working directory

Use:

/home/YOUR_PA_USERNAME/django-deployme

4.9 Configure the PythonAnywhere WSGI file

PythonAnywhere provides a WSGI file linked from the Web tab. This is the file you configure for the hosted web application. citeturn0search0

Use:

import os
import sys

path = "/home/YOUR_PA_USERNAME/django-deployme"

if path not in sys.path:
    sys.path.insert(0, path)

os.environ["DJANGO_SETTINGS_MODULE"] = "deployme.settings"

from django.core.wsgi import get_wsgi_application

application = get_wsgi_application()

Replace YOUR_PA_USERNAME.

LineMeaning
path = ...Location of the folder containing manage.py.
sys.path.insert(0,path)Makes the project importable.
DJANGO_SETTINGS_MODULETells Django which settings to load.
get_wsgi_application()Creates the WSGI application used by the web server.

4.10 Environment variables

Set the variables through the current PythonAnywhere web-app environment configuration mechanism:

DJANGO_SECRET_KEY = your-generated-secret
DJANGO_DEBUG = False
DJANGO_ALLOWED_HOSTS = YOUR_PA_USERNAME.pythonanywhere.com

Do not put the production secret into the repository. PythonAnywhere's existing-project guide points to its environment-variable configuration documentation for production settings. citeturn0search0

4.11 Static files

PythonAnywhere documents three main steps: set STATIC_ROOT, run collectstatic, then add a Static Files mapping in the Web tab. citeturn0search1

cd ~/django-deployme
python manage.py collectstatic --noinput

With our settings, the directory is:

/home/YOUR_PA_USERNAME/django-deployme/staticfiles

In the Web tab, under Static Files:

URLPath
/static//home/YOUR_PA_USERNAME/django-deployme/staticfiles

4.12 Reload

Click Reload in the Web tab. PythonAnywhere's documentation notes that a reload is required to publish changes to the live web application. citeturn0search2

4.13 Verify

https://YOUR_PA_USERNAME.pythonanywhere.com/

Test the home page, static assets, and /admin/ if configured.

PythonAnywhere mental model: code + virtualenv + Web app + WSGI + migrations + static mapping + reload.

5. Deployment 2 — Heroku

Heroku's current Python workflow is Git-centered: prepare the codebase, specify dependencies/runtime, provide a process declaration, configure environment variables, then push the Git branch to the Heroku remote. citeturn1search5turn1search7

Usage note: Heroku's current getting-started material notes that dynos/databases count toward usage and describes an Eco plan for its tutorial. Check current pricing and account requirements before creating resources. citeturn1search4

5.1 Install Git and Heroku CLI

git --version
heroku --version

On macOS with Homebrew:

brew install heroku/brew/heroku

The current Heroku CLI documentation identifies Git as a prerequisite. citeturn1search3

5.2 Login

heroku login

This opens the browser-based authentication flow. citeturn1search3

5.3 Specify Python version

Create .python-version at the repository root. Heroku currently recommends this file and says runtime.txt is deprecated.

3.14

Use a supported version compatible with the project you tested. Heroku's current Python runtime documentation recommends specifying the major version so security updates can be received automatically. citeturn1search1

5.4 Install and record Gunicorn

pip install gunicorn
pip freeze > requirements.txt

Heroku's Django configuration documentation requires a Procfile and recommends Gunicorn for Django web applications. citeturn0search9turn0search10

5.5 Create the Procfile

Create exactly Procfile in the project root — no .txt extension.

web: gunicorn deployme.wsgi

Understand it:

  • web: = web process.
  • gunicorn = production WSGI server.
  • deployme.wsgi = Django WSGI module.

Heroku's official Django guide shows the same pattern with a project-specific WSGI module. citeturn0search9

5.6 Check root structure

django-deployme/
├── .gitignore
├── .python-version
├── Procfile
├── requirements.txt
├── manage.py
├── deployme/
└── core/

5.7 Commit

git add .
git commit -m "Add Heroku deployment configuration"

5.8 Create the Heroku app

heroku create

Heroku creates the app and normally adds a Git remote named heroku. citeturn0search11turn1search7

Verify:

git remote -v

5.9 Configure environment variables

heroku config:set DJANGO_SECRET_KEY="PASTE_YOUR_GENERATED_SECRET"
heroku config:set DJANGO_DEBUG=False

Find the hostname:

heroku info

Then set:

heroku config:set DJANGO_ALLOWED_HOSTS="your-app-hostname"

Use the actual hostname shown for your app; do not literally use your-app-hostname.

Heroku's Django guidance recommends environment/config vars for sensitive configuration such as credentials. citeturn0search9

5.10 Deploy

If your branch is main:

git push heroku main

Heroku's Git documentation says pushing the main/master branch to the Heroku remote deploys the code. citeturn1search7

If your local branch is named something else, you can explicitly push it to Heroku's main:

git push heroku YOUR_BRANCH:main

5.11 Understand the build

git push→Python detected→Python runtime→pip install→collectstatic→release→Gunicorn

Heroku detects Python when appropriate dependency metadata such as requirements.txt is present and installs the listed dependencies. citeturn1search2turn1search6

Heroku also runs Django's collectstatic during a build unless that behavior is explicitly disabled. A failed collectstatic step can fail the build. citeturn1search0

5.12 Open and inspect the app

heroku open

If it fails:

heroku logs --tail

Refresh the site while the logs are visible.

5.13 Run migrations

heroku run python manage.py migrate

Create a superuser if needed:

heroku run python manage.py createsuperuser

5.14 Database warning

Do not treat a Heroku dyno filesystem as permanent database storage. SQLite is fine for learning the deployment mechanics, but a production application should use a persistent database service. Heroku's deployment guidance explicitly recommends using a database or object storage rather than depending on local filesystem writes. citeturn1search5

5.15 Optional PostgreSQL configuration

Once the basic deployment works, you can use a database URL rather than hard-coding a database connection. A common Django pattern is dj-database-url.

pip install dj-database-url
pip freeze > requirements.txt

Then:

import dj_database_url

DATABASES = {
    "default": dj_database_url.config(
        default=f"sqlite:///{BASE_DIR / 'db.sqlite3'}",
        conn_max_age=600,
    )
}

The exact PostgreSQL provisioning route depends on the current Heroku account, app generation, region, and available services. Follow the current Heroku database documentation when adding a persistent database.

5.16 Heroku mental model

Code→Git commit→Heroku app→Config vars→git push→Build→Gunicorn
Heroku checkpoint: The app should build successfully, start the web process, and be accessible from its Heroku URL.

6. PythonAnywhere vs Heroku

TopicPythonAnywhereHeroku
Deployment styleWeb-app configuration + virtualenv + WSGIGit push + build + process declaration
Python environmentConfigure a virtualenv for the Web appPlatform selects runtime and installs dependencies
Entry pointPythonAnywhere WSGI configurationProcfile → Gunicorn → Django WSGI
Static filescollectstatic + Web-tab Static Files mappingcollectstatic during build + WhiteNoise/common production strategy
Environment settingsWeb-app environment configurationHeroku config vars
UpdatePull/update files, run needed commands, reloadCommit + git push heroku main
LogsWeb-tab error/server logsheroku logs --tail

The biggest conceptual difference

PythonAnywhere exposes more web-server configuration. You explicitly connect code, virtualenv, WSGI, and static mapping.

Heroku abstracts more infrastructure. You give it a Git repository, runtime/dependencies, a process declaration, and configuration; the platform builds and starts the application.

8. Troubleshooting

ModuleNotFoundError: No module named 'django'

Check the PythonAnywhere virtualenv or confirm Django is in requirements.txt on Heroku. Install dependencies into the correct environment.

ModuleNotFoundError: No module named 'deployme'

Check the project path, WSGI module, and Procfile. The folder containing manage.py must be importable.

DisallowedHost

Your deployed hostname is missing from DJANGO_ALLOWED_HOSTS. Do not include https://; use the hostname.

CSS/static files are missing

Check django.contrib.staticfiles, STATIC_ROOT, collectstatic, and the host's static serving strategy. PythonAnywhere requires a Static Files mapping for the documented setup; Heroku's Django guidance recommends WhiteNoise. citeturn0search1turn1search0

Heroku build failed at collectstatic

Run locally: python manage.py collectstatic --noinput. Fix the actual error before pushing again. Heroku documents collectstatic as part of the build process. citeturn1search0

Heroku says Application Error

Run heroku logs --tail, refresh the site, and inspect import, settings, database, or Gunicorn startup errors.

PythonAnywhere says there was an error reloading

Check the Web-tab error log first. Common causes are incorrect WSGI path, missing dependency, incorrect settings module, or syntax/import errors.

It works with runserver but not Gunicorn

Run locally: gunicorn deployme.wsgi. If this fails, the problem is probably in dependencies, WSGI import path, settings, or application startup.

Debugging order

  1. Make it work locally.
  2. Run python manage.py check.
  3. Verify dependencies.
  4. Verify environment variables.
  5. Verify WSGI/Procfile.
  6. Verify static files.
  7. Read host logs.
  8. Then change hosting configuration.

10. Final Deployment Practice

Change the home page from:

Django deployment is working!

to:

Django Deployment Masterclass — Version 2

Deploy the change to both platforms.

Notice the different release workflow:

  • PythonAnywhere: update code → install changes if necessary → migrate/collectstatic if necessary → reload.
  • Heroku: change code → git add/commit → git push heroku main.
Final mental model: local Django → dependencies → production settings → static files → Git → host configuration → WSGI/process → environment variables → deployment → logs → live application → future releases.
